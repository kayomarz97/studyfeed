## Plain-language
Assemble everything the compiler built into ONE SQLite file the phone app reads — questions, flashcards,
reels, topic pages, the concept map, importance stars — plus a manifest describing the exam. The one hard
rule: build it twice from the same inputs and every item's **stable key** (the anchor the app pins your
progress/notes to) must be **identical**, so a future rebuild never orphans your data. Also: the 32
questions with no answer key get left out (unplayable).

## stable_key (§5j) — the reproducibility anchor
`stable_key = sha256(normalize(text) + '|' + work_id + '|' + page_ref)[:16]`, normalize = casefold +
collapse whitespace + strip punctuation. Use the **canonical** work_id (`workgroups.canonical_map(source_id)`)
so a re-supplied file yields the same key (§5b). Per table:
- **atom:** `normalize(statement) | canon_work_id | page_ref`
- **curated mcq:** `normalize(stem) | canon_work_id | page_ref`
- **generated mcq:** `normalize(stem) | "generated" | source_atom.stable_key` (no book provenance — derived)
- **concept / topic_page:** `sha256("concept|"/"topic|" + canonical_key)[:16]` (entity identity, not page)
Only these 4 tables carry stable_key (per schema). flashcards/reels anchor via `atom_id`. Duplicate keys
→ `INSERT OR IGNORE` + logged (deterministic).

## Manifest + checksums
- `pack_manifest.checksum` = **content checksum** = sha256 over sorted(all stable_keys) — deterministic,
  the reproducibility anchor (the .db file bytes are NOT reproducible: SQLite internal state + built_at).
- `manifest.json.checksum` = sha256 of the finished .db file (app import integrity/de-dup).
- manifest carries: schema_version (=PRAGMA user_version 1), pack_version "0.1.0", exam_code/name, built_at
  (UTC), feature_flags (has_concept_map, has_figures=false, has_dossiers, has_generated_mcqs), counts,
  importance_weights (profile) + histogram (playable feed_items), subjects, tag_defs. Validated vs
  manifest.schema.json.

## Reproducibility gate (the PATCH-01 blocker)
`verify()`: build twice to temp DBs → assert identical stable_key SET and identical content-checksum across
both builds. Incremental property ("add a source → pre-existing keys unchanged") holds **by construction** —
a stable_key depends only on that row's own normalized content + provenance, never on row order, counts, or
other rows — asserted + a subset-build spot check (keys from a half-atoms build ⊆ full-build keys). C13 does
NOT "pass" unless the twice-build is identical.
